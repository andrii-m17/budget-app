## 2. Базові фінансові визначення

| Показник | Формула / правило |
|---|---|
| Дохід | Сума `incomes` за місяць |
| Витрати | Сума `expenses` за місяць. **Включає** платежі по ОЧ. **НЕ включає** зміну балансу кредитних карток |
| Заощадження | Дохід − Витрати |
| Борг (карток) | Останній відомий залишок по кожній картці (carry-forward) |
| Обов'язкові платежі | Сума витрат з категоріями типу "Обов'язкова" (включно з ОЧ). Ретроспективний показник — "скільки я вже мусив віддати цього місяця" |
| Вільні гроші | Дохід − Обов'язкові платежі |

### Ключове правило: картки завжди окремо

Зміна балансу кредитної картки — **ніколи не витрата** і **ніколи не входить**
у "Обов'язкові платежі" / "Вільні гроші" / "Заощадження", навіть якщо йдеться
про мінімальний обов'язковий платіж. Причина: застосунок принципово не може
відрізнити "погашення з зарплати" від "перекидання грошей між картками" —
тому картки **завжди** живуть окремою метрикою "Борг", без спроби змішати
її з рухом готівки. **Повний Cash Flow не реалізовується** — цієї межі
достатньо.

## 3. Carry-forward та Data Integrity

### 3.1. Три часові шари — різні правила чесності

| Компонент | Правило при відсутності запису за місяць |
|---|---|
| KPI "Борг" (поточний стан) | Показує останнє відоме значення + позначку **"станом на [місяць]"** |
| KPI "Динаміка боргу" (дельта місяця) | Суворо: **"Немає даних за [місяць]"**, якщо бракує факту за поточний або попередній місяць |
| Графік "Динаміка боргу" | Справжній розрив лінії — жодної інтерпольованої/перенесеної точки |

### 3.2. Фактичний запис = лише через явне "Зберегти"

Запис боргу за місяць вважається **фактом** тільки якщо користувач явно
натиснув "Зберегти" цього місяця (навіть якщо число не змінилось).

```
Попередній місяць → pre-fill у полі → користувач перевіряє/змінює → Зберегти → факт
```

| Ситуація | Статус |
|---|---|
| Не відкривав / не зберігав | ⚠ Немає даних |
| Відкрив і зберіг те саме число | ✓ Фактичний запис |
| Відкрив і змінив число | ✓ Фактичний запис |

Окрема кнопка "Без змін" **не потрібна** — pre-fill + звичайне "Зберегти"
повністю вирішує проблему без нової UI-концепції.

> **Rev 2.17.0 — уточнення правила, ЛИШЕ для карток.** Явне підтвердження
> користувача (2026-09-16): pre-fill минулого місяця в поля "Борг по карті" /
> "Мін. платіж" створював фактичні записи-дублікати нового місяця, коли
> користувач відкривав картку в шторці й тис "Зберегти", навіть не
> усвідомлюючи, що там уже підставлене чуже (вересневе) число — на відміну від
> ОЧ, залишок картки не є оцінним значенням (не рахується формулою), а завжди
> факт з виписки банку, тому "здогадка" тут вводить в оману, а не допомагає.
> Тому для карток pre-fill **прибрано**: шторка відкривається з порожнім
> "Борг"/"Мін. платіж" (0), поки користувач сам не введе факт за цей місяць.
> Кредитний ліміт — виняток, це властивість самого банку (bankAccounts), а не
> щомісячний факт, тому й далі підставляється завжди.
> Це НЕ стосується: (а) ОЧ — carry-forward і далі рахується формулою
> (Модель C, §4-5 нижче), а не сліпо копіюється; (б) KPI "Борг"/аналітики
> (§3.1 вище) — там "останнє відоме значення станом на" лишається коректним,
> адже це вже НЕ pre-fill для нового факту, а прозоро позначена (⚠ "станом
> на") проекція існуючих фактів, коли новішого факту просто ще немає.

### 3.3. Деталізація дельти боргу (Картки / ОЧ)

- Назва KPI — фіксована: **"Динаміка боргу"** (не "Зменшення" чи "Збільшення" —
  назва не залежить від напрямку).
- Якщо борг не змінився: **"0 ₴ · без змін"** — нейтральний факт, без оцінних
  формулювань на кшталт "не скоротився".
- Під головним числом — розбивка: Картки / ОЧ окремо.
- Якщо один з двох компонентів не має даних за місяць — **показуємо частково**
  (Варіант B): головний KPI лишається обчисленим із доступних компонентів +
  позначка "частково — [компонент] не враховано"; НЕ ховаємо все число повністю.

### 3.4. Видалення картки/ОЧ зі списку

При видаленні — модалка з вибором місяця **"Приховати з..."** (замість
жорсткого "включно/виключно"). Дефолт — місяць, який зараз переглядається.
Історія до обраного місяця зберігається без змін; починаючи з обраного
місяця запис зникає з "Борги по картках" / Obligations. Те саме правило —
і для карток, і для ОЧ.

Додавання нової картки/ОЧ вже працює коректно (не потребує змін) — запис
природно не з'являється в місяцях до першого внесеного значення.

## 4. Модель залишку ОЧ (Модель C)

- **Фактичний залишок** — джерело істини, підтверджується користувачем
  щомісяця (pre-fill + Save, як і для карток).
- **Очікуваний залишок** — внутрішній контрольний розрахунок
  (попередній факт − сума прив'язаних витрат за місяць). **Не показується
  користувачу за замовчуванням.**
- Розбіжність факт/очікування — лише **інформаційне попередження**
  (наприклад, поріг 200 ₴ або 5%, значення уточнити при реалізації),
  ніколи не блокує збереження.
- Наступний місяць pre-fill будується **з фактичного**, а не з очікуваного —
  інакше похибка накопичується.

---

## 5. Витрата ↔ ОЧ: автозв'язок

Точна сума з витрати автоматично зменшує "очікуваний" залишок відповідного ОЧ.
Два способи прив'язки (обидва реалізуються):

- **B — швидкий екран "Оплатити ОЧ".** У Obligations біля кожного ОЧ — кнопка
  "Оплатити", яка відкриває форму витрати з передзаповненими назвою, сумою
  (з планового платежу, можна змінити) і вже встановленою прив'язкою.
- **C — автопідказка за назвою.** У звичайній формі витрат, якщо текст назви
  збігається з назвою ОЧ — показується підказка "Схоже, це платіж по «X» —
  прив'язати?". Списання залишку відбувається **тільки після явного
  підтвердження**, ніколи мовчки за самим фактом збігу тексту.

---

## 6. Obligations (нова вкладка/секція)

- **Замінює** нинішні таблиці "Борги по картках" + "ОЧ" в "Обліку" — одне
  джерело даних (`debts`), без дублювання.
- Охоплює: ОЧ + мінімальні платежі по кредитних картках. Оренда/підписки —
  поза межами цієї фази.
- Нові поля до записів боргу: день платежу (due day), чекбокс "оплачено".
- Мінімальний платіж по картці — вноситься вручну щомісяця (банк повідомляє
  суму, автоматичного розрахунку немає).
- Для ОЧ чекбокс "оплачено" вмикається автоматично через автозв'язок
  (розділ 5); для карток — вручну.

---

## 7. KPI "Борг" — три стани відображення

| Стан | Показує |
|---|---|
| Актуальні дані за поточний місяць | Число + напрямок зміни (як зараз) |
| Дані застарілі (carry-forward) | Число + жовта позначка "Станом на [місяць]" |
| Даних немає взагалі | "—" + "Немає даних" |

Формулювання — **"станом на"**, не "відносно" (останнє вже зайняте для
трендів і граматично означає порівняння, не знімок).

---

## 8. Що НЕ робимо в цій фазі (свідомо відкладено)

- Індикатор "Стан місяця" (Data Completeness banner) — цікаво, але не зараз.
- Повний Cash Flow з урахуванням довільних рухів коштів по картках —
  занадто неоднозначно з огляду на реальну поведінку користувача
  (перекидання коштів між картками).
- Мінімальні платежі по картках у "Обов'язкових платежах"/"Вільних грошах" —
  свідомо НЕ додаємо, картки завжди окремо.
- Оренда/підписки в Obligations — поза межами цієї фази.
