# SIM-1: автотести клавіатури й форм на симуляторі iOS

Мета: перевіряти екранну клавіатуру iOS без телефона. Playwright/WebKit її не показує, тому раніше це робив власник вручну. Лише інструменти: `index.html`, `sw.js`, `kb-*`, `inert`, фокус і формули не змінюються.

## Запуск
```
npm install                     # один раз (devDependencies: appium, webdriverio)
APPIUM_HOME=$PWD/.appium npx appium driver install xcuitest   # один раз (тека .appium у .gitignore)
npm run e2e:ios                 # усі чотири конфігурації, ≈ 3 хв
SIM_ONLY=iphone-portrait npm run e2e:ios   # одна конфігурація (iphone-portrait, iphone-landscape, ipad-portrait, ipad-landscape)
```
- Потрібні Xcode і симулятори. За замовчуванням `iPhone 16 Pro Max` і `iPad (10th generation)` (змінні `SIM_IPHONE`, `SIM_IPAD`).
- Сам запускає статичний сервер (`e2e/server.js`, порт 8937, `SIM_PORT`) і Appium (порт 4723, `SIM_APPIUM_PORT`); після прогону зупиняє їх.
- Застосунок іде з `http://localhost:8937/index.html?fixture=typical`: мок хмари, жодних справжніх даних, серверів Supabase немає.
- Код виходу 1, якщо хоч один сценарій не пройшов. У `pre-push-guard` не входить (довгий, потребує Xcode).

## Як це працює
- Appium + драйвер XCUITest, браузер Safari на симуляторі. Апаратна клавіатура вимкнена (`connectHardwareKeyboard: false`), тож з'являється екранна.
- **Фокус ставиться справжнім дотиком** (`mobile: tap` у NATIVE_APP), не програмно. Координати: два прозорі зонди (`#simprobe1`, `#simprobe2`) з доступними назвами; їхні положення в нативному дереві дають масштаб і зсув вікна перегляду.
- Лист відкривається викликом застосунку (`openCardDebtEditor`, `showProfileLoginForm`), як у наявних E2E; далі дотик у поле, перемикання, закриття дотиком по підкладці.
- Події беруться з рекордера застосунку (`startDebugRecording` → `debugEventBuffer`): `kb-geometry`, `sheet-open`, `sheet-anim`, `sheet-close`, `tabbar-restore`, `kb-frames`, `vv-resize`.
- Перед кожним листом робиться «прогрів» (одне відкриття/закриття без вимірювання) і перезавантаження сторінки.

## Сценарії (для кожної з чотирьох конфігурацій: iPhone і iPad × портрет і ландшафт)
Для двох листів: «Картка боргу» (`#cdd-balance` → `#cdd-limit`) і «Вхід» (`#cldfielda1` → `#cloud-password`):
1. Відкриття, дотик у поле: клавіатура з'явилась, фокус у цьому полі, `kb-open`, низ листа над краєм видимої області 8 ± 2 пт, `sheet-anim` (open).
2. Перемикання на друге поле: клавіатура лишилась, фокус змінився, лист не зсунувся більш ніж на 2 пт, стрибок `sheet-anim` (switch) ≤ 2 пт.
3. Закриття (дотик по підкладці): клавіатура зникла, видима область повернулась, `kb-open` знято, таб-бар видно й ≥ 21 пт від низу, `sheet-anim` (close).

## Пороги (наявні, нових не вигадано)
`sheet-anim`: не менше 12 кадрів (відкриття/закриття) і пауза ≤ 34 мс; низ листа на 8 пт над краєм видимої області (±2, як у тесті 36 `e2e/keyboard.spec.js`); таб-бар від низу ≥ 21 пт.

## Результати
`docs/ui/sim/<версія>/`: `summary.md` (сценарій → пройшов/впав → причина), JSON на сценарій (метрики, події), знімки до/після у JPEG (390 пт, якість 45). Якщо знімки сценарію разом > 300 КБ, вони видаляються й лишається лише JSON. `appium.log` лежить там же (його можна не комітити).
У JSON `sheetGapToNativeKeyboard` — довідковий зазор до справжньої клавіатури (верх з нативного дерева); у вкладці Safari він розходиться з `visualViewport` (див. нижче), тому вердикт ґрунтується на `visualViewport`.

## Вкладка Safari проти встановленого PWA (з головного екрана)
- Режим вкладки: `navigator.standalone === false`; є адресний і нижній рядки Safari; `visualViewport.height` при клавіатурі враховує й панель браузера (виміряно: 447 пт при клавіатурі 245 пт і вікні 796 пт, тож видима область менша за простір над клавіатурою на ≈ 140 пт). Саме тому цифри «над краєм видимої області» і «над справжньою клавіатурою» розходяться.
- Режим PWA (`standalone`): без панелей Safari, інша геометрія safe-area й `visualViewport`, і саме його використовує власник. Формули `kb-*` писано під нього.
- Отже `e2e:ios` перевіряє реальну екранну клавіатуру, події й анімацію, але геометрія вкладки не тотожна PWA. Сценарії, що падають лише через розбіжність `visualViewport`, треба підтверджувати на PWA.
- Чи можна автоматизувати PWA: не перевірено. Шлях: у Safari через нативні дотики «Поділитися → На початковий екран», потім запуск веб-застосунку з домашнього екрана й підключення Appium до його вікна (Web Inspector симулятора веб-застосунки показує). Ризики: нестабільні нативні кроки, інший bundle, потреба кожного прогону чистого встановлення. Окрема задача, якщо потрібна.

## Обмеження поточної версії
- Ландшафт iPhone: лист тіснить, дотик інколи не влучає в поле (збій прогону, не вердикт про застосунок); див. причини в `summary.md`.
- Симулятор повільніший за телефон: порушення порогу кадрів/пауз на кілька мс не обов'язково означають проблему на пристрої; рішення за власником.
