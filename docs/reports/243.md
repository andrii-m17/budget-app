# Дослідження 243 — перейменування ОЧ створює другий рядок у хмарі (клас C, Крок 0, лише дослідження)

Нічого не запушено, логіку, дані й вигляд не змінено. Додано `tests/och-rename-dup.test.js` (8 тестів: 4 пройшли, 4 `todo`, що падають на поточному коді; `node --test`: 1950 пройшло, 0 впало, 7 todo разом з 242). Усі назви синтетичні.

## Корінь одним реченням
Ідентичність ОЧ у хмарі тримається на `cloudId` на пристрої, але коли його немає, рядок шукається за ТОЧНОЮ назвою (`reconcileInstallmentAccountCloudId`, index.html:9074; `.maybeSingle()`), а при 0 збігів робиться `insert` із `created_at` = `createdAt` локального запису. Якщо між першою вставкою й моментом, коли пристрій запам'ятав id, назву змінили, перший рядок лишається живим (стара назва), а другий вставляється з тим самим `created_at` до мілісекунди. Це точно відповідає фактам із бази.

## 1. Відтворення (мок хмари з `accounts-dirty.test.js`)
- 243-1 (проходить, контроль): створити → синхронізувати → перейменувати → синхронізувати: один рядок, той самий id. Звичайне перейменування безпечне, коли `cloudId` відомий (push робить `update … eq('id')`, або CAS у `mdPushCas`).
- 243-2 (падає, `2 !== 1`: «Предмет А / Предмет Б»): `cloudId` втрачено після вставки + перейменування → два живі рядки з однаковим `created_at`. Це і є ваш симптом.

## 3. Пошук за назвою замість id (і що при 0 / кількох збігах)
- ОЧ `reconcileInstallmentAccountCloudId` (9074): 0 збігів → `insert`; ≥2 живих збігів → `.maybeSingle()` дає помилку, `existing` = null, код ігнорує помилку й теж робить `insert` (ще один дубль).
- Картки `reconcileBankAccountCloudId` (8882) і категорії (5061), підкатегорії (5343): те саме правило; у базі унікальність назв не дає вставити другий рядок (за вашими даними; я це не перевіряв).
- Словник `reconcileDictionaryCloudId` (5863): за ключовим словом без регістру, `limit(1)`, надгробки ігноруються.
- Pull ОЧ (9092): спершу `cloudId`, потім `byName` (прив'язує серверний рядок до локального запису з такою ж назвою й переписує його cloudId), потім додає як новий.
- Скидання cloudId за назвою: після помилки 23503 у `pushExpenseRecordPilot` (≈7984, `installmentAccounts.find(a.name === rec.linkedInstallment)`) і боргів (≈8262, `debtOwnerAccount`).
- Імпорт Excel і відновлення з копії: за назвою (див. вище).

## 5. Де cloudId втрачається або не виставляється
1. `pushInstallmentAccountsPilot` (9011): `acc.cloudId` присвоюється в пам'яті в `reconcile…`, а `saveInstallmentAccountsLocal()` викликається ОДИН раз після циклу по всіх брудних записах. Якщо застосунок призупинено/закрито (iOS), або мережа обірвалась між вставкою й цим збереженням, рядок у хмарі є, а на пристрої cloudId нема. Для пакетного першого завантаження (вересень) це стосується всіх вставлених записів до обриву. Тоді лікування за точною назвою працює лише доти, доки назву не змінили.
2. `applyCensus` (5492, 5505) скидає cloudId, якщо id нема в переписі; помилка 23503 (≈7984, 8262) і порожня відповідь `update` (9039) теж.
3. Відновлення з копії додає записи без cloudId (6198); Excel-імпорт створює записи без cloudId і без міток часу.
Як саме це сталося для вересневих записів, з коду не видно: потрібен пристрій власника.

## 6. Рекомендоване корінне виправлення (одне)
Ідентичність лише за id, видавати id на клієнті до першої відправки (як для витрат і боргів: UUID у `id`, `upsert onConflict id`). Тоді нема вікна «рядок є, id невідомий», `reconcile…` за назвою зникає з шляху відправки, а назва стає звичайним полем.
- Міграція: наявним записам без cloudId один раз зіставлення з серверним рядком за парою (`created_at` до мілісекунди + `initial_amount`), не за назвою; невпізнані лишаються новими з явним UUID.
- Пошук за назвою лише в Excel-імпорті, з підтвердженням (як і сказано в постановці).
- Додатково у тій же ревізії: гілка без `serverBase` (243-7) не шле `name`, якщо поле не змінене.
Вимоги до сервера: колонка `id` має приймати значення від клієнта (як у `expenses`); перевірте в чаті.
Чому не інакше: нормалізація назв («Предмет1» ≈ «Предмет 1») лише приховає частину збігів; «Об'єднати» (скасовано) не усуває причину; один лише `saveInstallmentAccountsLocal()` після кожної вставки закриває вікно 5.1, але не 243-4 і 243-6.
