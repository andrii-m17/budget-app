# AN-NEG · Крок 0: витрати з сумою ≤ 0 (клас C, лише читання)

## 1. Де підсумовуються витрати і що вони роблять із сумою ≤ 0
Спільне джерело: `monthAggregates(month)` (`index.html:15779`): `monthExp = activeExpenses()…`, `totalExpense = reduce(s + e.amount)` — **без фільтра за знаком**.
| Місце | Як рахує | 0 | < 0 |
|---|---|---|---|
| «Сімейний баланс», «Динаміка 6 міс.», частка «Потенціалу» (`totalExpense`), «Висновки» (`pct`, `savings`) | `monthAggregates` | не впливає на суму | **зменшує суму витрат** (додається зі знаком) |
| «Деталізація витрат» (`catBreakdown`, `analytics.js:1373`) | `if(!(a > 0)) return` (з 2.32.388) | відкидає | **відкидає** (джерело розбіжності з балансом) |
| Топ категорій у «Висновках» (`byCat`, `analytics.js:717`), «Звичка» (`countBySub`), `savingsPotential` (`:1577`) | `+ e.amount` без фільтра | 0 створює категорію/лічильник | зменшує суму категорії |
| «Обов'язкові»/«Вільні» (`mandatoryPaymentsSummary`, `:15797`) | `reduce` без фільтра | — | зменшує |
| Журнал: підсумок дня (`:15064`) | `reduce` без фільтра | — | зменшує |
| «Облік»/ОЧ: зв'язані платежі (`payments.js:252` `Number()||0`, `:837`, `index.html:11521`) | зі знаком | — | зменшує «внесено» |
| Експорт Excel (`:12797`) | пише `e.amount` як є | пише 0 | пише від'ємне; **імпорт такий рядок відхилить** (`normalizeAmount`) |

## 2. Шляхи введення
- Форма, редагування, дохід, ОЧ, модальне поле: `amount<=0` відхиляється (`10937`, `14195`, `11146`, `11983`, `20577`); `readPositiveAmount`/`normalizeAmount` (2.32.23) відкидають від'ємне, нуль, завелике.
- Імпорт Excel: `mapExcelExpenseRow` → `normalizeAmount`: ≤ 0 відхиляється (рядок рахується відхиленим).
- Monobank: `mono_accept…` бере `coalesce(p_amount, amount_uah)`; повернення — окрема `mono_apply_refund` (`v_new = amount − refund`; `v_new <= 0` → запис м'яко видаляється, а не стає 0/від'ємним). Чи може `amount_uah` бути 0 — не перевірено.
- **Хмара: `expenses_amount_check CHECK (amount >= 0)`** (і для `incomes`) — від'ємне на сервері неможливе, **нуль можливий**. Запис від'ємної суми з клієнта впаде з 23514 (запис лишиться «не синхронізованим»).
- **Без перевірки:** `pullExpensesCore` (довіряє серверу), відновлення з копії і читання локального сховища (`performRestore` сум не перевіряє). Отже від'ємне можливе лише локально: стара версія клієнта, відновлена копія, ручне редагування; нуль — і з хмари.

## 3. Фікстури
Лише `?fixture=invalid` (`dev/mock-cloud.js:66`): `amount = -5`, `0`, `1.5`, `'12'`, `2147483647` — навмисно «брудні дані» для стійкості клієнта, не повернення. Решта фікстур: суми 50–2050 (> 0). Повернення Monobank (`refund_*`) у фікстурах — окремі поля, не від'ємні суми.

## 4. Варіанти
| | Вплив на суми | `FINANCIAL_RULES` | Синхронізація |
|---|---|---|---|
| (а) заборонити на введенні й імпорті, наявні — з позначкою «перевірити» | Введення вже заборонене; суми не змінюються, розбіжність «баланс ≠ деталізація» лишається, поки записи не виправлено | не торкається формул | нічого нового (виправлення — звичайне редагування) |
| (б) від'ємні = повернення скрізь | Змінює зміст (витрата стає доходом/зменшенням) і дублює `refund_*` | потребує нового правила | **ламає**: сервер відхиляє від'ємне (CHECK), потрібна міграція сервера |
| (в) скрізь відкидати ≤ 0 | Баланс = деталізація; суми зникають лише там, де такі записи є | вхідний набір, не формула (потрібне явне підтвердження: у коментарі `monthAggregates` «формулу не змінювати») | нічого (записи лишаються в базі й журналі) |

## 5. Рекомендація
(в) + м'яка частина (а): одне спільне правило «враховується лише сума > 0» у `monthAggregates` (звідки беруть баланс, динаміка, потенціал, висновки, обов'язкові) та у зв'язаних сумах ОЧ; записи лишаються в журналі, їх легко знайти й виправити (позначка «перевірити» — окремо, клас B). (б) відхиляю: сервер це забороняє, повернення вже мають свій механізм. Перед змінами чат має порахувати в робочій базі `amount = 0` (від'ємних бути не може) і, за потреби, попросити одноразову подію самописця з кількістю локальних записів ≤ 0 (лише число). Чекаю підтвердження.

## Доповнення (рішення чату): чи може клієнт надіслати `amount = 0` у хмару (лише читання)
Усі шляхи відправки беруть `rec.amount` як є, без перевірки: `pushExpenseRecordPilotCore` `index.html:5212`, `pushExpensesBatch` `:5310`, `pushIncomeRecordPilotCore` `:5386`, `pushIncomesBatch` `:5424`, CAS-оновлення `mdSnap` `:4642`/`:4668` (надсилає лише змінені поля). Тож нуль піде в хмару лише якщо він уже є в локальних даних; створити його застосунок не може:
- надгробок/видалення: **ні** (CAS шле лише `deleted_at`; повний рядок із `amount` — лише для запису, якого ще нема на сервері, `:5212`/`:5386`); редагування: **ні** (`amount<=0` відхиляється, `:14195`; категорію/підкатегорію CAS шле без суми); форма/дохід/ОЧ: **ні** (`:10937`, `:11146`, `:11983`); імпорт Excel: **ні** (`normalizeAmount`, `:12871`/`:12888`); прийняття з Monobank: **ні** (клієнт не передає `p_amount`, `grep p_amount index.html` порожній; сервер бере `amount_uah`, повернення при `v_new <= 0` м'яко видаляє, а не пише 0); `e2e:cloud` і юніт-тести: **ні** (суми 55/100/333…; нулів у `e2e/cloud/*` нема).
- **Єдиний теоретичний шлях — відновлення копії** (`performRestore`, `:7161`, суми не перевіряє) і застарілі локальні дані: нуль, якщо він уже був у файлі/сховищі. Наслідок під CHECK `amount > 0`: відправка цього запису падає (23514), пакет іде в поштучний резерв, запис лишається «не синхронізованим» (ERR-2 повторює ≤ 3 рази за сеанс), інші записи не страждають; даних не губиться. У робочій базі таких записів 0 (перевірено чатом).
- Фікстура `?fixture=invalid` (`dev/mock-cloud.js:66`: `-5`, `0`) лише ВІДДАЄ такі значення клієнту з мока; у робочу базу не пише (preview/тести працюють на моку) — нормально.
- **Висновок: застосунок не створює `amount = 0`, можна посилювати CHECK** (`> 0` для `expenses` і `incomes`). Застереження: відновлення дуже старої копії з нулем лишить один запис неотправленим; за бажання клієнт може відхиляти ≤ 0 при відновленні (окрема задача, клас B/C).
