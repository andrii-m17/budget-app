# OCH-CLOSE · Крок 0 (без змін коду застосунку)

## 1. Залишок ОЧ
- Єдине джерело: `installmentChainCalc` (js/payments.js:186) → `estimateInstallment(name, month)` / `resolveInstallmentFact` (index.html ≈ 11530–11575). Залишок місяця M = max(0, початок M − сума прив'язаних витрат M); початок M = внесений факт M (опора) або кінець попереднього місяця (FINANCIAL_RULES §4.1). Лише цілі гривні (суми цілі).
- «Останній платіж» = найпізніша прив'язана витрата (`e.linkedInstallment === name` або `linkedInstallmentId`, без `deletedAt`); його місяць = `monthKey(e.date)`. Залишок після нього = `estimateInstallment(name, thatMonth).balance`.

## 2. Шляхи внесення платежу
(а) форма «Витрати» з підтвердженою прив'язкою (`saveExpense`, ≈ 10953); (б) вибір ОЧ у панелі редагування витрати (≈ 14219); (в) «Оплатити» з «Платежів» і з шторки ОЧ (`payInstallmentPrefill`, `payInstallmentQuick`) — це та сама форма (а); (г) Monobank: `mono_accept` на сервері створює витрату з `p_installment_id`, до клієнта вона приходить через Realtime/pull (≈ 5747–5777); (д) відновлення з копії й синхронізація з іншого пристрою; (е) ручний запис боргу в шторці ОЧ (`saveInstallmentDrawer`, ≈ 11960).
- Висновок: шляхи (г), (д) не проходять через локальну дію користувача, тому тригер «залишок ≤ 10» краще **виводити з даних** (на рендері ОЧ-списку й після синхронізації), а не вішати на одну подію збереження.

## 3. Наявне приховування — і вже наявна пропозиція (Rev 2.32.69)
- Ручне: «Прибрати зі списку» → `removeInstallmentAccount` → `showMonthPickerModal` → `hideEntityFromMonth(hideKey(name,'installment'), fromMonth, …)` → `saveHiddenFrom()`; запис `hiddenFrom[key] = { month, updatedAt, accountName? }`, у хмарі `hidden_from_month`. Видимість: `isHiddenForMonth` (month ≥ entry.month, tombstone `deletedAt` = «показано назад») і `isInstallmentVisibleForMonth` (+ нижня межа початку ОЧ). Історія минулих місяців лишається, бо перевірка йде за місяцем перегляду.
- **Пропозиція «Погашена ОЧ» уже є:** `installmentPaidOffOffer` / `offerHidePaidOffInstallment` / `applyHideInstallmentFrom` (index.html ≈ 12005–12041), підпис у рядку «Погашено · Приховати з <місяць>» (`.cdr-paidoff`) і діалог після збереження запису з залишком 0 (≈ 11970). Місяць = наступний після останнього запису (`paidOffHideFromMonth`). Нічого не ховається без підтвердження; «Не зараз» нічого не пише.
- **Розрив:** наявна логіка дивиться на ЗАПИСИ боргу (`debts`: balance ≤ 0 або платіж ≥ попереднього залишку), а не на ланцюжок із прив'язаних витрат. Платіж, прив'язаний через форму витрат (шляхи а, б, в, г), запису боргу не створює, тож пропозиції не буде; поріг зараз 0, а не 10.

## 4. Сценарії (очікувана поведінка)
| Сценарій | Очікування |
|---|---|
| Залишок після платежу 1 ₴ | ≤ 10: пропозиція; місяць платежу видимий, приховати з наступного |
| 100 ₴ | не пропонуємо |
| 10 ₴ (рівно) | пропонуємо (≤ 10) |
| Часткові платежі | рахуємо залишок після кожного; пропозиція лише коли ≤ 10 |
| Переплата | залишок 0 (max(0, …)): пропонуємо |
| Видалення/відміна останнього платежу після приховування | автоматично не повертаємо (приховування — окреме рішення користувача); діалог не повторюється; «Показати назад» уже є (tombstone). Залишок знову > 10 → рядок «Погашено» зникає, якщо ще не прихована |
| Два пристрої | приховування через `hidden_entities` (LWW за `updated_at`); пропозиція показується на тому, де користувач вніс платіж; на іншому — тихий підпис, не діалог |
| Офлайн | запис у чергу як зараз (`saveHiddenFrom`), показ локальний |
| Прихована вручну раніше | пропозиції немає (`isHiddenForMonth` для місяця) |
| Редагування суми платежу | залишок перераховується; пропозиція зникає/з'являється за порогом |
| ОЧ без терміну | залишок з `initial_amount` і платежів; без `initial_amount` залишок невідомий (`null`) — пропозиції немає |
| Приховування вже минулого місяця | `from` = наступний за місяцем останнього платежу, не раніше |
