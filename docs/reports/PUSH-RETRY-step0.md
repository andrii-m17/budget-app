# PUSH-RETRY · Крок 0 (без змін коду)

1. **Виклик функції.** `push_send` (baseline, ≈ рядок 1413) генерує `push_id`, кладе в `data`, пише архів і `push_sent_log`, застосовує `hide_details` і робить `net.http_post` на send-push-notification із заголовками `push_call_headers()` (`Authorization` anon, `x-push-secret` із vault). Тіло: `{ user_id, title, body, data }`. Функція читає лише ці поля (`data.type` → TTL/urgency, `data.push_id` → журнал; `pushIdOf` приймає лише UUID).
2. **sub_id.** `push_subscriptions.id` — випадковий uuid, не похідний від endpoint; у `statuses` безпечний (журнал і так бачить лише власник за RLS, чиститься за 7 днів). Endpoint, p256dh, auth у журнал не потрапляють і далі.
3. **Повтор, коли підписки нема.** З `only_subs` функція фільтрує підписки користувача (чужі id ігноруються за побудовою: `getSubs` за `user_id`); відсутній id → запис `{ ok: false, status: null, reason: "sub_gone", sub_id, transient: false }`, без відправки, у `failed` не рахується; якщо всі `sub_gone` — відповідь 200 `{ sent: 0, failed: 0 }`.
4. **Межі transient.** Так: `send_failed` зі status 429, ≥ 500, 408 і без status (мережа, таймаут); `exception`, `subs_read_error`, `auth_check_error`. Ні: 400, 401, 403, 404, 410, 413 та інші 4xx; `no_subscriptions`, `config_missing`, `sub_gone`. Рядки без sub_id (exception, subs_read_error): повтор усім підпискам користувача, бо нічого не відправлялось.
5. **Колонка attempt до міграції.** Рекомендую не фіча-ознаку, а той самий прийом, що вже є для `push_id`: якщо вставка журналу дала помилку про `attempt`, повторити без цієї колонки (узагальнити на кілька колонок). Тоді порядок деплою не важливий.
6. **Ризики.** Мережевий збій без status може означати «дійшло, але відповідь загубилась» → можливий дубль (той самий `push_id`; клієнт квитанції не дублює, але сам показ у iOS ні; для mono-inbox працює tag). Приймаємо. У `baseline.sql` колонки `push_id` нема (її додав чат окремою міграцією): міграцію `attempt` чату варто покласти в `supabase/migrations`.
