### 1.2 Сервер (читанням, без змін)
- `incomes` не має колонки джерела: це `note`. Тригери: `set_updated_at_if_changed` (змінений рядок → `updated_at = now()`, `updated_by` зберігається), `trg_deleted_at_server`, `trg_purge_epoch`. Тому SQL-перенесення 19 записів **бампає `updated_at`** і клієнти підтягнуть їх через дельту/Realtime.
- `build_other_actor_summary_for(user, since, until)` бере доходи з `updated_at` у вікні, автор = `coalesce(updated_by, created_by)`; якщо автор ≠ отримувач, формує push, а для одного доходу тіло = `coalesce(note,'Дохід') · сума`. Наслідки: (а) масова правка 19 рядків породить зведення «змінено N доходів» для іншого учасника; (б) текст push міститиме `salary_1`, поки функція не навчена мапити id у нейтральний підпис.
- Інших серверних місць, що читають `incomes.note`, немає (перевірено пошуком по міграціях і Edge-функціях).

## 2. Підпис «ЗП …» без імен у коді

Мета: у репозиторії лише нейтральні id і запасні підписи; ім'я учасника береться з даних родини, що вже є в базі (`users.display_name`) і вже вантажиться (`loadFamilyUsersDirectory`).

| Варіант | Як визначаємо, чий слот `salary_N` | Плюси | Мінуси й ризики |
|---|---|---|---|
| **A (рекомендую)** | нова колонка `users.salary_slot` (1, 2 або `null`), ставить чат (2 рядки); клієнт читає її в тому ж запиті, що й `display_name`/`gender` | явно, однаково на всіх пристроях, не залежить від порядку створення; змінюється без релізу | потрібна міграція схеми (чат, клас C); `select` з новою колонкою падає на сервері без неї — тому спершу сервер, потім клієнт; старі клієнти колонку не вибирають і не зламаються |
| B | слот = порядок `users.created_at` (перший учасник — 1) | без зміни схеми | крихко: додавання/видалення учасника міняє підписи; приховане правило |
| C | налаштування на пристрої («Мій слот: 1/2») | без сервера | кожен пристрій окремо, можливі суперечності; ручна дія |
| D | нейтральні підписи назавжди («Зарплата 1», «Зарплата 2») | найпростіше, жодних даних | втрата зручності: не видно, чия зарплата |

Підпис: `«ЗП » + display_name` (коротко: перше слово `display_name`; `push_name` не використовуємо, бо він для сповіщень). Те саме джерело підпису для плиток, шторки, Журналу, Кошика, діагностики, подій інших учасників (замість `key`).

**Що бачить користувач:**
| Стан | Підпис |
|---|---|
| Дані родини ще не завантажились, першого запуску з кешем нема | «ЗП 1», «ЗП 2», «Інше» (нейтрально) |
| Після першого онлайн-входу | «ЗП ім'я N» і кеш підписів у `localStorage` (як `budget-author-genders-v1`; імена лишаються лише на пристрої, не в репозиторії) |
| Офлайн, кеш є | підписи з кешу |
| Офлайн, кешу немає (новий пристрій) | «ЗП 1», «ЗП 2» |
| Слот без учасника (`salary_slot` не задано, один учасник) | «ЗП 1/2» без імені |
| Учасника перейменовано | підпис оновиться при наступному завантаженні довідника; старі записи не чіпаємо (в них id) |

**Колір.** Плитки доходу мають власні кольори за слотом (синій, фіолетовий), колір автора — за `users.gender` (рожевий/синій) для рамок і сповіщень. Пропозиція: нічого не змінювати (нейтрально); необов'язково пізніше — колір плитки за статтю власника слота (це змінює вигляд, окреме рішення). З варіантом A зв'язок слот → учасник → стать вже доступний.

## 3. План фази 2 (запис нейтральних id)

### 3.1 Принцип
Усі межі працюють у просторі **id** (`salary_1`, `salary_2`, `other`); старе значення розпізнається лише на читанні. Без імен у коді старі ключі («Зарплата ім'я N») розпізнаємо **у виконанні**: `'Зарплата ' + display_name` кожного учасника з довідника, прив'язаного до слота. Імпорт Excel не потребує імен (позиція колонки).

### 3.2 Порядок кроків (жоден пристрій не ламається)
1. **Перевірка версії другого телефона** (п. 3.5). Пристрій не нижче 2.32.121 уже розуміє id.
2. **PRIV-2a** (клієнт без зміни даних): імена зникають з тестів, документів, коментарів, реєстру «Перевірок»; охоронний тест.
3. **Сервер, крок 1 (чат):** `users.salary_slot` для 2 учасників (DDL + 2 рядки).
4. **PRIV-2b** (клієнт, клас C): `INCOME_SOURCES` без імен; підписи з довідника; запис id; нормалізація на межах (читання локальних даних, pull, `snapFromRow`, імпорт Excel, відновлення з копії, експорт з підписом замість сирого ключа); умова `local.source !== cloudSource` → через `sameIncomeSource`; тести з умов рев'ю 2.32.121.
5. **Підтвердження:** обидва пристрої на PRIV-2b (через «Перевірки» або вручну).
6. **Сервер, крок 2 (чат):** перенесення 19 записів на id у транзакції з перевіркою й відкатом; правка push-функції; керування зведеннями (п. 3.4).
7. Після цього нових старих ключів ніхто не створює; розпізнавання старих лишається (старі копії, Excel).

### 3.3 Синхронізація: LWW і Realtime
- Старе й нове значення — один і той самий запис за `sameIncomeSource`, тож жоден рядок не стає «іншим джерелом».
- Перенесення на сервері змінює `note` → тригер бампає `updated_at`, `updated_by` лишається авторським → клієнти тягнуть рядок дельтою/Realtime, `local.source` стає id без нового push (запис чистий).
- Одночасна правка: пристрій А (ще старий ключ) і пристрій Б (id) змінюють суму того самого доходу. Якщо поле `source` порівнювати сирим текстом, виникне хибний конфлікт «Джерело». Тому в `MERGE_DOMAINS.incomes` значення джерела нормалізується до id перед порівнянням (тест).
- Брудний локальний запис зі старим ключем (офлайн-правка) при зустрічі з серверним id: merge приймає серверне джерело як рівне, суму/дату зливає за правилами домену; зайвого push немає (тест «Cloud-рядок із нейтральним ключем не створює зайвого push»).
- М'яко видалені записи (`deleted_at`) переносяться разом з іншими (вони теж у `note`).

### 3.4 Побічні ефекти масової правки на сервері (для чату)
1. `updated_at` бампнеться в 19 рядках: це бажано (клієнти підтягнуть).
2. **Зведення «інший учасник змінив N доходів»** піде іншому учаснику за 20 хв вікно. Щоб його не було: виконувати поза вікном і одразу після `UPDATE` встановити `notification_state.last_run_at` (`job_name = 'other-actor-summary'`) для обох учасників у `now()` — або під час тихих годин, але тоді «since» не просувається і зведення прийде після них. Рекомендація: зсунути `last_run_at` у тій самій транзакції.
3. Текст push для доходу: у `build_other_actor_summary_for` замінити `coalesce(it->>'note', 'Дохід')` на мапінг `salary_1/salary_2/other` → «Зарплата 1»/«Зарплата 2»/«Інші доходи» (без імен на сервері не потрібні; або `'Дохід'`). Робити **до** переносу, інакше перший push після нього прочитає «salary_1».
4. Приблизний SQL (приклад для чату; без імен, виконується в транзакції з перевіркою й відкатом):
```sql
begin;
select note, count(*) from public.incomes group by 1 order by 1;             -- до: 6 / 6 / 7 за старими ключами
update public.incomes set note = case note
    when '<стара назва 1>' then 'salary_1'
    when '<стара назва 2>' then 'salary_2'
    when 'Інші доходи'     then 'other' end
  where note in ('<стара назва 1>', '<стара назва 2>', 'Інші доходи');
select note, count(*) from public.incomes group by 1 order by 1;             -- після: 6 / 6 / 7 за id, старих 0
-- перевірити: updated_by не змінився, updated_at змінився лише в цих рядках
-- керування зведеннями: update public.notification_state set last_run_at = now() where job_name = 'other-actor-summary';
rollback;  -- для тесту; для застосування — commit
```

### 3.5 Імпорт Excel і відновлення
- Імпорт «Історія»: колонки B/C/D → `salary_1`, `salary_2`, `other` за позицією (імен не потрібно); `alreadyExists` порівнює через `sameIncomeSource`.
- Експорт: колонка «Джерело» = підпис (з довідника; запасний «ЗП 1») замість сирого значення.
- Відновлення з копії (старі копії мають старі ключі): при відновленні значення нормалізуються до id; невідомі рядки лишаються як є (це користувацькі дані, не код).
- Локальні старі записи: тихий перехід при першому завантаженні довідника — без зміни `updated_at` і без push (дані та сама сутність).

### 3.6 Телефон на старій версії (нижче 2.32.121)
Після перенесення на сервері він отримає `note = salary_1`, а його `INCOME_SOURCES` знає лише старі ключі: плитка «Доходи» покаже 0 для цього джерела (запис існує, на екрані «Облік» невидимий; у «Аналітиці» його сума рахується); збереження плитки створить **дубль** зі старим ключем (подвійний дохід). Тому перенесення на сервері — лише після підтвердження версії.

**Як чату перевірити версію (читанням, без особистих даних):**
- (а) `client_debug_logs` за `user_id` другого учасника: `app_version`, `created_at` (лише ці поля, 1 рядок). Зараз записів немає.
- (б) Опублікувати у реєстрі «Перевірок» крок «Відкрийте застосунок і закрийте цей крок» (як 2.32.202-1). Результат пишеться в `client_debug_logs` (`scenario = 'check'`) з `app_version` і `user_id`; шапка «Перевірок» показує «Збірка X». Працює для версій від 2.32.202; відсутність результату за кілька днів = стара версія або пристрій не відкривали.
- (в) Ручна: екран «Налаштування» → «Версія застосунку» (або нижній підпис «Money Tree · Rev …»); попросити назвати/сфотографувати.
- (г) Опційно — серцебиття версії при вході (нова мала таблиця/колонка): це серверна зміна й окрема ревізія; рекомендую лише якщо (б) і (в) не підійдуть.

### 4.2 Документація й коментарі
13 файлів документації, 3 макети, коментарі в `index.html`, `css/app.css`, `css/tokens.css`, `js/analytics.js`: «Рішення власника», «Підтвердив …», «ім'я … бачить скачок» → «власник»/«користувач»; записи ROADMAP зі справжніми прикладами переписати нейтрально (це редагування поточного тексту, не історії git).

### 4.3 Знімки (192 кандидати)
`docs/ui/ds-3a`, `ds-3b`, `ds-3b4`, `ds-3c3`, `ds-n1…ds-n4` (екран «Облік», 64 файли), їхні зведення (10), `docs/ui/sim/2.32.248/255/258/259` і `UI-1` (знімки шторки доходу, 118). Це «до/після»-знімки конкретних ревізій; перезняти «до» неможливо.
- Варіант 1 (рекомендую): `git rm` цих файлів у PRIV-2d, посилання в їхніх `summary.md` позначити «знімки прибрано»; нові знімки робити лише з нейтральними підписами (після PRIV-2b вони автоматично нейтральні).
- Варіант 2: лишити (імена видно в історії все одно).
- Варіант 3: перезняти актуальні версії, старі прибрати.
Важливо: до PRIV-2b не комітити нові знімки «Обліку» й шторки доходу.

### 4.4 Охорона від повернення імен
Тест `tests/no-real-names.test.js`: перебирає текстові файли репозиторію, розбиває на слова, хешує (SHA-256, нижній регістр, основа слова) і порівнює з файлом хешів імен — самого переліку імен у репозиторії немає. Для облікового запису GitHub — окремий допустимий список файлів (п. 1.5).
