# LOGIN-FORM-4: стан «входимо» після автозаповнення (Rev 2.32.329, клас C)

Стан: реалізовано, не запушено (чекає слова чату).

## Проблема (MT-1117-7227, 2.32.328)
Вхід через велику панель Face ID працює, але за 1,6 с форма 5 разів змінювала положення, слідуючи за висотою клавіатури 388 → 311 → 388 → 415 → закрито; iOS прокручував сторінку на 1–3 пт, і наш код відповідав 5 `pan-comp`. Пауза 140 мс з 328 для цього закоротка.

## Зроблено
1. **Стан «входимо»** (`loginLock`, `loginLockOn` / `loginLockOff`). Вмикається на першому `change` у полі входу, що збігається з `:-webkit-autofill`. Поки діє (і лише для `profile-drawer`, `kbLoginLockOn`), конвеєр клавіатури не міняє положення й висоту форми: `updateKbSheetGeometry` (зміни висоти клавіатури, `kb-vv-resize`, прокрутка сторінки) виходить одразу; `correctPanIfNeeded` не коригує зсув (немає `pan-comp` / `pan-corrected`); у `handleKeyboardFieldFocusIn` перекидання фокуса, яке робить iOS, лише запам'ятовується (`native-focus` / `switch-native` форму не рухають). Закриття через `blur` / `focusout` не заблоковане: форма закривається як зазвичай.
   Вимикається: форму закрито (`closed`), вхід завершився (`submitted`: успіх або помилка; повідомлення про помилку як раніше), або за 1000 мс друге поле не заповнилось і вхід не триває (`timeout`, подання немає). Ручний набір і дотики без стану працюють без змін.
2. **Подання.** `change` у полі з автозаповненням викликає `loginAutoCheck` одразу (без 300 мс): обидва поля не порожні й обидва з `:-webkit-autofill`, вхід не триває, пару значень ще не подавали → `blur` активного поля (в `loginFormSubmit`) і один `requestSubmit()`. Те саме після завершення групи `autofill`. Для `input` (посимвольне заповнення) лишено паузу 300 мс, щоб не подати частково заповнений пароль: це відхилення від «одразу» лише для `input`.
3. **Пауза 140 мс з 328 (`KB_PAN_SETTLE_MS`) лишена.** Стан «входимо» покриває лише автозаповнення форми входу; перекидання фокуса, яке iOS робить без автозаповнення (тест 136: `vvOffsetTop` 1↔2 при зміні висоти), ним не покривається. Тест 136 (з вимоги ТЗ) лишився зеленим.
4. **Самописець.** `login-lock` з `on` і `reason` (`timeout`, `submitted`, `closed`); значень полів не пишемо.

## Тести (лише цільові)
- WebKit `keyboard.spec.js`: 137a (послідовність 7227: заповнення пошти, фокус на пароль, висота 583/506/479 від базової, прокрутка 1–3 пт, заповнення пароля: положення форми не змінюється ±0,5, 0 `pan-comp` / `pan-corrected`, один вхід `by autofill`; на 2.32.328 положення рухалось: 355 → 431,7), 137b (заповнилось одне поле: `login-lock` `on` → `off timeout` через 1 с, подання немає; на 2.32.328 подій `login-lock` не було). 80, 132, 136 зелені.
- `login-return.spec.js` 44a–c, 134a–d, 135a, 135c–e (11 passed). Юніт 2167, `e2e:smoke` 10 passed.

## Відхилення і ризики
- Для `input` лишено паузу 300 мс (див. п. 2); `change` подає одразу.
- Заблоковане положення форми означає, що, якщо висота клавіатури справді змінилась назавжди (наприклад, панель Face ID → клавіатура), форма стоїть на положенні першого заповнення до подання або 1 с: після подання форма закривається.
- Реальні висоти 583/506/479 і прокрутка 1–3 пт на моку відтворюються підміною `visualViewport`; чи вистачить 1000 мс між першим і другим заповненням на пристрої, покаже `login-lock` у звіті.

## Крок для «Перевірок»
Вийти з акаунта, торкнутись пошти, підтвердити Face ID (велика панель), 8 секунд нічого не торкатись, 5 разів; окремо рядок підказки над клавіатурою. Результат: після заповнення форма стоїть на місці (не стрибає між 388 / 311 / 415), вхід іде сам. У звіті: `login-lock` `on` → `off` (`submitted` або `closed`), `login-submit by: autofill`, 0 `pan-comp` після першого заповнення.
