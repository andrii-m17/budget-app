# MERGE-REF: злиття «поле за полем» для довідників і прихованих (Крок 0 і план; код не змінювався)

## 1. Поля по доменах
| Домен | Можуть зливатись | Не зливаються (ідентичність/зв'язки) |
|---|---|---|
| `categories` | `type`, `active` (deletedAt) | `name` (ключ зіставлення за назвою; перейменування = нова/стара гілка), `cloudId`, `createdAt` |
| `subcategories` | `active`, `deactivated_via` | `name` + батьківська `category_id` (разом ключ), `syncedCategoryId`, `cloudId` |
| `dictionary` (слова) | `deleted_at/deleted_via` | `keyword` (ключ, lower), `category_id`, `subcategory_id` (пара зв'язків: зливати лише разом), `syncedCategoryId/SubcategoryId`, `cloudId` |
| `bank_accounts` | `credit_limit`, `payment_day` (`paymentDayPayload`), `name` | `cloudId`, `createdAt` (ключ місяців/боргів), id як ключ приховування |
| `installment_accounts` | `initial_amount`, `due_day`, `term_months`, `start_date`, `first_payment`, `pay_mode`, `payment`, `name` | `cloudId`, `createdAt` |
| `hidden_entities` | `hidden_from_month`, `deleted_at` (одне «рішення» — див. п. 4) | ключ `(entity_type, entity_id=cloudId)`, локальний `installment:#<cloudId>` |

Назва: у картках/ОЧ вона й ключ зіставлення, і редагована. Зараз push робить `update … eq(id)` з клієнтським `updated_at` (сервер тепер його перезаписує, тригери 22.10 і `trg_set_updated_at_insert`), pull — LWW за `updatedAt` + «чистий запис не вважається новішим» (`isDirty`). Зліпок `serverBase/serverUpdatedAt/localRev/syncedRev` (SHADOW-REV) для цих доменів уже ведеться: push-шлях `shadowSnap/shadowSetServer/shadowAfterPush` є в усіх шести.

## 2. Особливості й ризики
- **Дублі:** UNIQUE за назвою свідомо немає (категорії/картки/ОЧ). Злиття не створює дублів саме по собі, але reconcile-за-назвою («є живий рядок із такою назвою → прив'язатись») лишається єдиним захистом; у словах є часткова унікальність `(family_id, lower(keyword)) where deleted_at is null` (код 23505 → повторний пошук). Перейменування на двох пристроях на одну назву дасть два рядки з однією назвою: потрібне правило «той, хто програв, не створює нового, а прив'язується».
- **Надгробки 14 днів:** категорії/підкатегорії/картки/ОЧ мають purge cron; злиття «видалення проти правки» тут небезпечніше, ніж у витрат: видалення категорії каскадно ставить `deleted_at` слів і підкатегорій (`deleted_via`). Правка проти каскадного видалення має трактуватись як «видалено» без картки.
- **Перейменування ОЧ:** назву ОЧ ведуть тригер `trg_sync_debt_names` і клієнт за `accountId` (борги/витрати/ключі приховування). Якщо назва ОЧ стане зливаним полем, її конфлікт потрібно вирішувати до розсилки на борги; рекомендація: назву ОЧ і картки НЕ зливати (останній за сервером), решту полів зливати.
- **Самозцілення `cloudId`:** `update … eq(id)` без рядка = «висячий id» → скидання й reconcile за назвою. Умовний update (`updated_at = serverBase`) дасть той самий порожній результат і при конфлікті, і при висячому id: потрібен один GET `by id` (як у витрат), щоб розрізнити.
- **«Вічно брудні»:** підкатегорії без батька, слова без `cloudId` ніколи не отримають серверної бази; їх не зливати (лишити старий шлях upsert/reconcile), інакше вони блокуватимуть злиття або вічно конфліктуватимуть. Домени з пропущеним зліпком уже мають такий запасний шлях (як у витрат).
- **Старі пристрої:** записи без `serverBase` йдуть старим шляхом (як у витрат).

## 3. Конфлікти: картка чи тиха політика
- **Картка «Оля вже змінила…»:** ліміт і день платежу картки; платіж, сума, місяці, дата, спосіб ОЧ; назва картки/ОЧ (тихо «сервер переміг», але з рядком у журналі конфліктів). Фінансові значення, які людина вводить руками й пам'ятає.
- **Тиха політика «сервер переміг» (без картки, лише діагностика):** категорії (`type`, `active`), підкатегорії, слова: структура рідко змінюється одночасно, а картка «Повернути моє» для переміщення слова між категоріями плутає. `active` — мовчки останній за сервером.
- Журнал конфліктів уже має `dom`/`kind`; додаються лише `conflictModel` для картки й ОЧ (етикетки полів у `CONFLICT_FIELD_ACC`: `credit_limit`, `payment_day` тощо).

## 4. Приховування
Запис = один «набір» `{ hidden_from_month, deleted_at }` на ключ `(тип, cloudId)`; ключ уже за cloudId, тож перейменування не заважає. Правила: (а) обидва приховують — місяці різні: перемагає **раніший** місяць? Ні: це один запис, перемагає останній за сервером (бо «місяць початку приховування» не сумується); (б) один приховав, інший повернув (`deleted_at`): пара полів зливається **разом** як одне рішення, конфлікт = дві різні дії над одним ключем → тиха політика «сервер переміг» + toast «Оля вже приховала/повернула», без картки «Повернути моє» (повернення — одним тапом у UI). (в) Не зливати поля окремо: `month` від одного й `deletedAt` від іншого дадуть стан, якого ніхто не обирав. Запис лишається upsert на UNIQUE `(family_id, entity_type, entity_id)`; умовний update потрібен лише для існуючого рядка за `updated_at`.

## 5. План малими Rev (кожен — клас C, спочатку Крок 0-підтвердження)
| Rev | Група | Ризик | Суть |
|---|---|---|---|
| A | Картки + ОЧ | середній | `MERGE_DOMAINS.bank_accounts/installment_accounts`: поля п. 1, назва — «сервер», картка конфлікту для ліміту/платежу; `rowCtx`/`pushCtx` без `linked`; виняток: зіставлення за назвою лишається |
| B | Категорії + підкатегорії | середній | Тиха політика, лише `type/active`; каскад видалення без картки; батьківські зв'язки поза злиттям |
| C | Слова | низький-середній | Лише `deleted_at/deleted_via`; пара `category_id/subcategory_id` — один «зв'язок», не зливається; 23505-шлях збережено |
| D | Приховані | низький | Пара-рішення, тиха політика + toast |
Тести кожного Rev: два пристрої на моку (`two-devices`, `MockCloud.otherDevice`), «годинник ±1 доба» (годинник пристрою не бере участі: перевірити, що зміна клієнтського `updated_at` ±1 доба не міняє переможця), різні поля мовчки зливаються, те саме поле → картка/тиха політика, видалення проти правки, висячий `cloudId`, запис без зліпка, офлайн→онлайн, перейменування ОЧ + борги, дубль назви, E2E на моку.

## Від сервера (робите ви)
1. Підтвердити, що `set_updated_at_if_changed` (BEFORE UPDATE) і `trg_set_updated_at_insert` діють на всіх шести таблицях (`hidden_entities` теж) — інакше умовний update не має опори.
2. Для умовного update: можливість `update … eq(updated_at)` з поверненням рядка вже є (RLS); окремих RPC не потрібно.
3. За потреби: частково-унікальні індекси на живі `name` (категорії, картки, ОЧ; `(category, name)` підкатегорій) — лише з вашого рішення, зараз свідомо немає; без них дублі ловить reconcile.
4. Перевірити cron purge: чи не прибирає рядки раніше за 14 діб при каскадному видаленні.
Після звіту зупиняюсь, чекаю рішення.
