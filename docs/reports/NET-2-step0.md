# NET-2 · Крок 0: скільки запитів дає одна дія з доходом, боргом, ОЧ, рахунком, категорією (клас C, лише читання)

Код і сервер не змінено. Виміри: мок хмари (`?fixture=typical`), WebKit, `window.__netStats` (`NET_STATS`) до/після дії + 3,5 с очікування (щоб Realtime-луна власного запису й відкладена перевірка встигли відпрацювати). Дія = те, що викликає UI: зміна локального запису → `save*` → `push*Pilot`. Тимчасовий вимірювальний тест видалено, не комітився. Синтетичні дані.

## 1. Виміри (запитів на одну дію)

| Область | Додати | Змінити | Видалити (надгробок) | Склад запитів (змінити) |
|---|---|---|---|---|
| Витрати (NET-1, еталон) | **1** | **1** | **1** | `PATCH expenses` |
| Доходи | 4 (першого разу 8*) | **4** | **4** | `PATCH incomes` + `GET incomes` ×2 + `RPC sync_heads` |
| Борги | 4 | **4** | **4** | `PATCH debts` + `GET debts` ×2 + `sync_heads` |
| ОЧ (`installment_accounts`) | 7 | **7** | не виміряно** | `PATCH` + `GET installment_accounts` ×2 + `GET hidden_entities` + `GET expenses` + `GET debts` + `sync_heads` |
| Рахунки-картки (`bank_accounts`) | 7 | **6** | не виміряно** | `PATCH` + `GET bank_accounts` ×2 + `GET hidden_entities` + `GET debts` + `sync_heads` |
| Категорії | 7 | **6** | не виміряно** | `PATCH` + `GET categories` ×2 + `GET subcategories` + `GET dictionary` + `sync_heads` |

\* Перше «додати доходи» містить ще 4 `GET` (`categories`, `subcategories`, `dictionary`, `expenses`): це відкладена перевірка після попередніх витрат (відомий наслідок NET-1: «побачена голова» `expenses` не просувається, тож перша наступна перевірка робить `sync_heads` + `GET`). Власний внесок доходу = 4.
\** Видалення ОЧ, карток і категорій у застосунку йде не одним `deletedAt`+push, а каскадами (кошик/надгробки, `hidden_entities`, перепис дітей); синтетичний варіант дав лише один `GET` і не репрезентативний. Реальний шлях треба виміряти в першій ревізії відповідної області.

Звідки зайве (доходи, борги): запис (1) + негайний `GET` власної таблиці після успіху (`pull` у `push*Pilot`, якщо не `suppressPull`) (2) + Realtime-луна власного запису → `sync_heads` (3) + ще один `GET` за зміненою «головою» (4). Для ОЧ/карток/категорій до цього додаються **залежні таблиці** (`SYNC_DEPENDENTS`: ОЧ → `hidden_entities`, `expenses`, `debts`; категорії → `subcategories`, `dictionary`; картки → `hidden_entities`, `debts`), бо зміна «голови» батька тягне дітей.

## 2. Що з NET-1 можна перевикористати

- `suppressPull` (`pushIncomeRecordPilot/pushDebtRecordPilot` уже приймають; працює в пакетах): готовий вимикач негайного `pull`.
- Загальні `MERGE_DOMAINS.incomes/debts` (`cols: INC_ROW_COLS/DEBT_ROW_COLS`, `snapFromRow`, `mdMergeServerRow`, `mdPushCas`): рядок із відповіді можна застосувати тим самим злиттям, що pull.
- Гасіння Realtime-луни: `SELF_ECHO` + `selfEchoBegin/Finish/Check` ключ — `id` запису (UUID), `updated_at` в UTC-мікросекундах, `updated_by = я`, TTL 15 с. Табличний лише в події самописця (`'expenses'` вшито в `selfEchoEvent`): потрібен параметр таблиці. Realtime-обробник зараз гасить лише витрати (охоронний тест `net1-echo`: «доходи й борги не чіпались»).
- Не перевикористати напряму: `expRetFull`/`EXP_ROW_COLS` і `expApplyPushedRow` (специфіка витрат: alias `category` від `expenses_resolve_refs`, `created_by`, ОЧ). Для доходів і боргів це простіше (немає alias), але потрібен свій `applyPushRow`; борги мають FK-контекст (картка/ОЧ за id, `monthlyPayment/minPayment` необов'язкові).
- Для рахунків і категорій механізм інший: `push*Pilot()` без параметрів пушить увесь список «брудних» записів і сам ставить `cloudId`; відповідь upsert треба читати як рядки, а не один запис.

## 3. Ризики

- **Два пристрої:** луна гаситься лише коли збігаються `id` + `updated_at` (мікросекунди) + `updated_by = я`; чужий запис і запис з іншого пристрою того ж користувача з іншим `updated_at` не гаситься. Для доходів/боргів/рахунків гасіння «зайвого» нічого не втрачає лише якщо відповідь запису застосовано; інакше лишається старий шлях (як у NET-1).
- **«Побачена голова» не просувається** (NET-1): перша наступна перевірка робить `sync_heads` + `GET` за таблицею. Для ОЧ/карток/категорій це ще й залежні таблиці (≈ 5 запитів одним разом). Тож для **одиночної** правки економія мала (7 → 1 зараз + ≈ 6 при наступній перевірці); виграш є, коли кілька правок підряд (батч правок = один відкладений набір) і коли користувач не повертається з фону одразу. Просувати голову без звірки небезпечно (можна пропустити чужу зміну).
- **Офлайн:** запис у черзі (`autoSyncStale`) іде старим шляхом (`suppressPull` лише за застосованим рядком); при помилці/0 рядків/конфлікті лишається повний pull.
- **Дані:** узгодженість `cloudId` (self-heal), каскад перейменувань, `hidden_entities`: помилка тут псує зв'язки (клас C, фінансові дані).

## 4. План ревізій і очікувані запити

| Ревізія | Область | Що | Було → стане (одна дія) |
|---|---|---|---|
| NET-2a | Доходи | повний рядок у відповіді + `applyPushRow` + `suppressPull` при успіху + гасіння луни (параметр таблиці в `selfEchoEvent`, дозвіл у Realtime-обробнику) | 4 → **1** |
| NET-2b | Борги | те саме + FK-контекст (картка/ОЧ), необов'язкові поля | 4 → **1** |
| NET-2c | ОЧ і рахунки-картки | `push*Pilot` читає рядки відповіді, гасіння луни за id списку, без негайного `pull`; перед тим виміряти реальне видалення | 7 → **1–2** (+≈ 5 відкладених залежних одним набором) |
| NET-2d | Категорії, підкатегорії, слова | те саме | 7 → **1–2** (+≈ 3 відкладені) |

Для кожної: юніт (як `net1-echo`), E2E WebKit `NET_STATS` до/після (додати, змінити, видалити, відновити; з Realtime і без), `e2e:cloud` на двох пристроях, `spec-reviewer`, зупинка до «можна пушити». Кожна окремо (одна ревізія = одна область).
