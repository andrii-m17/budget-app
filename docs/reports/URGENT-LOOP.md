# URGENT-LOOP: цикл запитів `bank_accounts` (клас C, Крок 0, без коду)

Дата: 22.10.2026. Реальних даних немає (в логах лише агреговані числа; id, IP і ключі не наводяться).

## Підсумок
Причину знайдено й **відтворено на моку**: нескінченна взаємна рекурсія `pushBankAccountsPilot` ↔ `pullBankAccountsCore`, що не робить жодного запису на сервер, лише читає. Запускає її стан «локальний `updatedAt` новіший за серверний `updated_at`, але запис вважається синхронізованим». Такий стан породжує сервер: тригер `set_updated_at_if_changed` ігнорує `updated_at` клієнта. Сервер у циклі не винен, зміни на сервері не потрібні (за винятком рішення про тригер, див. варіант C).

## Докази
- **Логи API за добу (агреговано):** `GET /bank_accounts` 11 539 запитів; решта таблиць по 20–40 (норма). Усі 11 102 основних запити однакові: `select … &updated_at=gte.<одна й та сама мітка>&order=updated_at.asc,id.asc&limit=500` з `https://andrii-m17.github.io/`, iPhone (iOS 18.7), **жодного `PATCH`/`POST` у `bank_accounts`** (лише `GET` і `OPTIONS`). Хвилі: ≈ 20:38–21:58 UTC (≈ 80 хв), пік ≈ 6 500 запитів за 15 хв (≈ 7 запитів/с). Мітка в запиті не змінювалась (2026-10-19), тобто мітку цикл не рухає.
- **Відтворення (мок `typical`, Rev 2.32.113):** локальному рахунку з найновішим серверним `updated_at` ставимо `updatedAt = syncedUpdatedAt =` майбутній час, скидаємо мітки, один `pullBankAccountsCore()` → цикл: за 3 с **48 401 виклик pull і 48 401 push** (мережі в моку немає, тому швидко); на реальній мережі ≈ 7/с. Без скидання міток цикл не стартує (дельта не повертає цей рядок).
- **Сервер (читання визначень):** на `bank_accounts` тригер `BEFORE UPDATE trg_set_updated_at` → `set_updated_at_if_changed()`: якщо після `UPDATE` дані (без `updated_at`/`updated_by`) не змінились, `new.updated_at := old.updated_at` (значення клієнта ігнорується); якщо змінились, `new.updated_at := now()` (теж не значення клієнта). Раніше це було записано лише в ROADMAP.

## Механізм (де саме)
1. `pullBankAccountsCore`: для рядка зі збігом `cloudId`, якщо `localTime > cloudTime` → `keptLocal++; pushBankAccountsPilot(); continue` (без `await`, без перевірки, чи запис «брудний»).
2. `pushBankAccountsPilot`: `planBankAccountsPush` бере лише «брудні» (`syncedUpdatedAt !== updatedAt`); запис не брудний → `plan.push` порожній → нічого не надсилається → `if(!anyError) await pullBankAccountsCore()` (безумовно, навіть коли нічого не пушилось).
3. Назад на п. 1 з тим самим рядком (він стоїть на мітці: `updated_at >= мітка − 2 с`, мітка = його ж `updated_at`) → цикл. Пауз, лічильника й виходу немає.
Той самий шаблон «pull → keptLocal → push; push завершується pull» є ще в `categories`, `subcategories`, `dictionary`, `installment_accounts`, `hidden_entities` (6 таблиць; `expenses`/`incomes`/`debts` мають інший шлях). Тобто це латентна вада всіх шести; вистрілила лише для карток.

## Як виникає стан «локальний новіший, але синхронізований»
Сервер ніколи не зберігає `updated_at` клієнта. Після будь-якого `push` клієнт ставить `syncedUpdatedAt = updatedAt` (своє значення), а на сервері лежить інше:
- (а) **no-op оновлення:** `updatedAt` на пристрої змінився без зміни даних (штамп часу, відновлення з копії, перезапис того самого значення) → тригер лишає старий `updated_at` → на сервері старіше, ніж локально;
- (б) **годинник пристрою попереду серверного:** після реальної зміни сервер ставить `now()` (серверний), що менше за клієнтський штамп.
Яка саме з гілок на тому iPhone, **не встановлено** (потрібні дані з пристрою; див. «Не перевірено»).

## Вартість
≈ 11 100 зайвих запитів за 80 хв (проти ≈ 25 на повну звірку), батарея й квота запитів Supabase; сервер відповідав 200 щоразу.

## Варіанти виправлення
| | Що | Плюси | Мінуси |
|---|---|---|---|
| **A** (рекомендую, основа) | У `pull*Core` викликати `push` лише для **брудних** записів (`syncedUpdatedAt !== updatedAt`), інакше вважати сервер переможцем за змістом і **прийняти серверні `updated_at` (локальний `updatedAt = syncedUpdatedAt = row.updated_at`)**; у `push*Pilot` завершальний `pull` лише якщо щось справді надсилалось. Після успішного `UPDATE` брати з відповіді `updated_at` сервера (він вже повертає рядок) і ставити його локально | усуває причину для всіх 6 таблиць; сервер вважається автором `updated_at` (як і є фактично) | торкається логіки LWW у 6 таблицях (клас C): потрібні тести «локальний новіший і чистий», «двоє пристроїв», «годинник попереду» |
| **B** (запобіжник, окремо й завжди) | Рахунок спроб: не більше 3 циклів pull → push → pull за 60 с на таблицю, далі пауза 60 с (потім 5 хв) і запис події в діагностику (`NET_STATS`/журнал); реентерабельний захист `pushXPilot` (якщо вже виконується, не стартувати) | зупиняє будь-яку подібну петлю, навіть невідому; дешево | не лікує причину; якщо живе без A, дані лишаються «розсинхронізованими» мовчки |
| **C** | Сервер: тригер приймає `updated_at` клієнта (для рядків, де дані змінились) | клієнт і сервер збігаються | змінює серверну логіку LWW (тільки чат), ризик для двох пристроїв; не потрібен, якщо є A |
| **D** | Лишити як є, прибрати `await`-less `push` з `pull` | найпростіше | втрачається «донести переможну локальну версію одразу» |

**Рекомендація:** A + B одним Rev (клас C), або B першим окремим Rev (малий ризик, зупиняє витік запитів одразу), A наступним.

## Матриця сценаріїв (для реалізації)
