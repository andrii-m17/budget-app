# Тестування: протокол тестових варіантів

Розділ «Тестування» (Сервіс → «Тестування») — єдине місце, де в застосунку
живуть тестові варіанти функцій і запис діагностики. Цей документ — правила
гри, щоб варіанти не накопичувались.

## Коли додається тестовий варіант

Лише коли рішення **не можна прийняти без перевірки на пристрої** (поведінка
залежить від iOS/WebKit, жесту, анімації тощо). Якщо питання вирішується
читанням коду, документації чи тестами — варіант не потрібен.

## Правила

1. **Максимум 3 активних тести одночасно** (Rev 2.32.0, F: `motion-intensity` і `card-reveal` завершено — реєстр порожній; Rev 2.30.0, M4b: `button-style` завершено — «Скло» єдиний стиль — тож ліміт, тимчасово піднятий до 4 у Rev 2.27.0, повернено до 3; зараз діють `motion-intensity` і `card-reveal`; `dashboard-replay` завершено в Rev 2.31.0 (M4c) — «Щоразу» стала єдиною поведінкою) (захисний тест у
   `tests/pilot-repository.test.js` це перевіряє на реєстрі `TEST_VARIANTS`).
2. Кожен тест має **критерій прийняття** (у `what`/`checkSteps` і в промті
   ревізії) — за яким числом/спостереженням обирається переможець.
3. Кожен запис має **правило прибирання** (`cleanupBy`) — умову, за якої його
   треба видалити.
4. Увесь код варіантів читає значення **лише через `getVariant(id)`**; ключ
   `localStorage` `budget_variants_v1` читається тільки в модулі реєстру
   (`<test-variants-module>` у `index.html`) і **не входить** у
   `BACKUP_LS_KEYS`.
5. Після рішення — **одна ревізія «finalize»**: видаляє програшні варіанти
   (код і гілки), запис реєстру, застарілі події/поля рекордера, що існували
   лише для порівняння; `pruneVariants()` при старті прибирає збережений вибір
   з `localStorage`. Поведінка для користувача після finalize — лише
   переможний варіант.
6. У `docs/ROADMAP.md` ведеться розділ **«Testing log»**: для кожного тесту —
   `id`, варіанти, рішення, дата (див. шаблон нижче).

## Як додати тест (запис реєстру `TEST_VARIANTS`)

```js
{
  id: 'kebab-case-id',              // унікальний, kebab-case
  title: 'Коротка назва',
  what: 'Одне речення: що саме перевіряємо.',
  variants: [                        // ≥2, ключі унікальні
    { key: 'a', label: 'Варіант A', hint: 'Що змінюється для користувача' },
    { key: 'b', label: 'Варіант B', hint: '…' },
  ],
  defaultVariant: 'a',               // серед variants
  addedIn: 'Rev X.Y.Z',              // ревізія, що додала тест
  cleanupBy: 'умова видалення',      // напр. «після рішення за логами X»
  checkSteps: ['Крок 1', 'Крок 2'],  // 2–3 кроки перевірки на пристрої
}
```

Код варіанта: `if(getVariant('kebab-case-id') === 'b'){ … } else { … }`.
Екран «Тестування» сам показує картку (назва, «Що перевіряємо», перемикач
варіантів із `hint`, позначка «типовий», `addedIn`/`cleanupBy`, «Як перевірити»,
«Записати лог із цим варіантом» — відкриває запис діагностики зі сценарієм
`<id>-<variant>`, «Скинути до типового»). Обраний варіант потрапляє в лог:
`device.variants` = `{ id: обраний_варіант }`.

## Шаблон запису «Testing log» (docs/ROADMAP.md)

| id | Варіанти | Рішення | Дата |
|---|---|---|---|
| `kebab-case-id` | `a` (типовий), `b` | обрано `b`: коротка причина з цифрами логів | YYYY-MM-DD |

## Ізоляції тестових записів немає (Rev 2.32.81, ISOL-1)

Ізоляцію тестових імен (`TRASH-TEST-*`, `isTestSyncIgnored`, `filterTestRows`, прапорець `budget_ignore_test_prefix_v1`, кнопка «Очистити тестові записи на цьому пристрої»; Rev 2.23.32) прибрано повністю: записи з будь-якою назвою, зокрема з префіксом `TRASH-TEST-`, синхронізуються (push, pull, перепис id, автосинхронізація) і видаляються однаково. Префікс більше не гарантує безпеки: це лише позначка для пошуку й видалення.

- **Автоматичні тести й preview не пишуть у робочу базу** (правило не скасовано): воно не залежить від імен. Його гарантують мок за замовчуванням для будь-якого origin, крім `https://andrii-m17.github.io` (`dev/mock-cloud.js`, `?fixture=`), fail-closed визначення середовища і захисник «лише перегляд» у режимі «Реальні дані · лише перегляд» (Rev 2.32.75, 2.32.78).
- Тестові записи в реальній базі (ручна перевірка, наприклад «Видалити назавжди» для кожного типу): називати помітно («ВИДАЛ-1»), видаляти через «Видалити назавжди» в Корзині (воно йде на сервер: витрата, дохід, слово, місячний борг — `DELETE`; картка, ОЧ, категорія — надгробок до 14 днів, див. `docs/SUPABASE_POLICY.md`). Залишки на сервері чистить лише чат (SQL).
- Порада: тестувати на окремій тестовій родині (окремий акаунт у Cloud) або на моку.

## Правило тестових даних у preview з живою Cloud-сесією (Rev 2.28.1)

Якщо в preview-браузері є жива Cloud-сесія (тестова чи ні): (1) **створювати лише витрати** з префіксом `TRASH-TEST-` і **лише через застосунок**, одразу прибираючи їх «Видалити назавжди»; (2) **не створювати** в Cloud картки, ОЧ, категорії, підкатегорії, борги, доходи; (3) ізоляції тестових імен більше немає (Rev 2.32.81): записи синхронізуються як звичайні, тож називай їх помітно і видаляй через «Видалити назавжди»; з живою сесією preview працює лише як «Реальні дані · лише перегляд» (запис заблоковано); (4) дані «для знімків» сідити лише в пам'яті сторінки (без збереження й без `renderAll` у режимі, де можливий push), після чого перезавантажити сторінку; (5) після сесії перевірити SQL-ом, що нових рядків у Cloud немає.

## Перевірка нових текстових полів (Rev 2.31.4)

Текстові поля вводу не повинні викликати панель iOS «Автозаповнити контакт»: у `id` і `name` не використовувати підрядки `name`, `phone`, `tel`, `mail`, `addr`, `user`, `login`, `first`, `last`, `fio`, `contact` (без урахування регістру); нові поля — абстрактні id (`fld` + код + число). Порядок перевірки нового поля: (1) додати id до `KNOWN_TEXT_FIELD_IDS` у `tests/input-attrs.test.js` після перевірки; (2) відкрити відповідну модалку/шторку в preview й переглянути `runInputAttrsAudit()`; (3) на iPhone — «Запис діагностики», торкнутися поля, «Мітка», у логу шукати `input-focus-audit` для цього поля (`fieldForbidden` має бути `null`).

## Безповоротне видалення карток і ОЧ (Rev 2.32.4, T2)

«Видалені дані» → «Борги» / «ОЧ»: приховані картки й ОЧ та видалені місячні записи мають «Видалити назавжди» (лише онлайн, з Cloud-сесією). Картка/ОЧ у Cloud отримує `deleted_at` (tombstone), її місячні борги — теж, запис прихованого прибирається; сервер остаточно видаляє такі рахунки через 30 днів (`purge_deleted_accounts`). Локально рахунок зникає з усіх списків одразу, інший пристрій прибирає його при синхронізації.

**Важливо: старий застосунок (нижче 2.32.4) не знає про `deleted_at` і може показати видалену картку чи ОЧ знову** (і навіть створити такий самий рахунок заново). Тому безповоротно видаляйте рахунки лише після того, як ОБИДВА телефони оновились до 2.32.4+.

Тестові дані: картки/ОЧ у Cloud створювати лише помітними назвами (ізоляції за префіксом більше немає, Rev 2.32.81) і видаляти через цю функцію; решту залишків чистить чат SQL-ом. Без прапора тестові рахунки не синхронізуються (видалення локальне).
