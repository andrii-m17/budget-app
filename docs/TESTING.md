# Тестування: протокол тестових варіантів

Розділ «Тестування» (Сервіс → «Тестування») — єдине місце, де в застосунку
живуть тестові варіанти функцій і запис діагностики. Цей документ — правила
гри, щоб варіанти не накопичувались.

## Коли додається тестовий варіант

Лише коли рішення **не можна прийняти без перевірки на пристрої** (поведінка
залежить від iOS/WebKit, жесту, анімації тощо). Якщо питання вирішується
читанням коду, документації чи тестами — варіант не потрібен.

## Правила

1. **Максимум 4 активних тести одночасно** (Rev 2.27.0, M2.1: ліміт ТИМЧАСОВО піднято з 3 до 4, поки діють `motion-intensity`, `dashboard-replay`, `card-reveal`, `button-style`; після вибору на iPhone тести прибираються окремою ревізією й ліміт повертається до 3) (захисний тест у
   `tests/pilot-repository.test.js` це перевіряє на реєстрі `TEST_VARIANTS`).
2. Кожен тест має **критерій прийняття** (у `what`/`checkSteps` і в промті
   ревізії) — за яким числом/спостереженням обирається переможець.
3. Кожен запис має **правило прибирання** (`cleanupBy`) — умову, за якої його
   треба видалити.
4. Увесь код варіантів читає значення **лише через `getVariant(id)`**; ключ
   `localStorage` `budget_variants_v1` читається тільки в модулі реєстру
   (`<test-variants-module>` у `index.html`) і **не входить** у
   `BACKUP_LS_KEYS`.
5. Після рішення — **одна ревізія «finalize»**: видаляє програшні варіанти
   (код і гілки), запис реєстру, застарілі події/поля рекордера, що існували
   лише для порівняння; `pruneVariants()` при старті прибирає збережений вибір
   з `localStorage`. Поведінка для користувача після finalize — лише
   переможний варіант.
6. У `docs/ROADMAP.md` ведеться розділ **«Testing log»**: для кожного тесту —
   `id`, варіанти, рішення, дата (див. шаблон нижче).

## Як додати тест (запис реєстру `TEST_VARIANTS`)

```js
{
  id: 'kebab-case-id',              // унікальний, kebab-case
  title: 'Коротка назва',
  what: 'Одне речення: що саме перевіряємо.',
  variants: [                        // ≥2, ключі унікальні
    { key: 'a', label: 'Варіант A', hint: 'Що змінюється для користувача' },
    { key: 'b', label: 'Варіант B', hint: '…' },
  ],
  defaultVariant: 'a',               // серед variants
  addedIn: 'Rev X.Y.Z',              // ревізія, що додала тест
  cleanupBy: 'умова видалення',      // напр. «після рішення за логами X»
  checkSteps: ['Крок 1', 'Крок 2'],  // 2–3 кроки перевірки на пристрої
}
```

Код варіанта: `if(getVariant('kebab-case-id') === 'b'){ … } else { … }`.
Екран «Тестування» сам показує картку (назва, «Що перевіряємо», перемикач
варіантів із `hint`, позначка «типовий», `addedIn`/`cleanupBy`, «Як перевірити»,
«Записати лог із цим варіантом» — відкриває запис діагностики зі сценарієм
`<id>-<variant>`, «Скинути до типового»). Обраний варіант потрапляє в лог:
`device.variants` = `{ id: обраний_варіант }`.

## Шаблон запису «Testing log» (docs/ROADMAP.md)

| id | Варіанти | Рішення | Дата |
|---|---|---|---|
| `kebab-case-id` | `a` (типовий), `b` | обрано `b`: коротка причина з цифрами логів | YYYY-MM-DD |

## Ізоляція тестових записів `TRASH-TEST-` (Rev 2.23.32, 6D.201)

Тестові дані в реальному Cloud (родина Андрія й Олі) повертались на пристрої й назад: самолікування (перепис id) бачить «живий запис, якого немає в Cloud» і створює його знову, навіть якщо його свідомо видалили SQL-ом. Тому:

- Запис, чия **назва / нотатка / слово починається на `TRASH-TEST-`** (регістр неважливий; лише початок: «Мій TRASH-TEST-1» і «Тестова картка» НЕ збігаються), **ігнорується синхронізацією** на пристрої: pull його не додає, перепис id не відтворює, push (поодинокий, пакетний, hidden) не відправляє.
- Вимикач: `localStorage.budget_ignore_test_prefix_v1`. За замовчуванням (ключа немає або будь-що, крім `'0'`) ізоляція УВІМКНЕНА. Значення `'0'` вимикає її.
- **Сесії, де треба перевіряти саме синхронізацію тестових записів** (live-тест G-серії, відновлення/видалення назавжди на `TRASH-TEST-` даних): виставити `localStorage.setItem('budget_ignore_test_prefix_v1','0')` ДО створення даних і **повернути (`removeItem`) одразу після тесту**; після прапора 0 очистити Cloud SQL-ом і кнопкою нижче. Нюанс: pull інкрементальний (маркер `updated_at`), тож рядки, пропущені при ввімкненій ізоляції, не «довантажуються» заднім числом після вимкнення — скидайте маркери (`budget_sync_markers_v1`) для повного перетягування.
- **Кнопка «Тестування» → «Очистити тестові записи на цьому пристрої»:** збирає локальні записи з префіксом (картки, ОЧ, борги, витрати, доходи, категорії, підкатегорії, слова, приховані), показує підсумок («2 картки, 1 ОЧ, 2 борги, …»), після підтвердження видаляє їх ЛОКАЛЬНО (без push і без tombstone; Cloud не змінюється — його чистить чат SQL-ом). Подія рекордера `test-cleanup` — лише кількості.
- Порядок прибирання тестів з реальних Cloud-даних: (1) на всіх пристроях — кнопка очищення; (2) SQL у порядку `hidden_entities` → `debts` (+ `expenses` ОЧ) → `bank_accounts`/`installment_accounts`; (3) перевірити, що записи не повернулись після відкриття застосунку.
- Порада на майбутнє: тестувати на окремій тестовій родині (окремий акаунт у Cloud) — тоді тестові записи взагалі не доходять до справжніх пристроїв.
