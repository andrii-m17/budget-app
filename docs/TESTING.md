# Тестування: протокол тестових варіантів

Розділ «Тестування» (Сервіс → «Тестування») — єдине місце, де в застосунку
живуть тестові варіанти функцій і запис діагностики. Цей документ — правила
гри, щоб варіанти не накопичувались.

## Коли додається тестовий варіант

Лише коли рішення **не можна прийняти без перевірки на пристрої** (поведінка
залежить від iOS/WebKit, жесту, анімації тощо). Якщо питання вирішується
читанням коду, документації чи тестами — варіант не потрібен.

## Правила

1. **Максимум 3 активних тести одночасно** (захисний тест у
   `tests/pilot-repository.test.js` це перевіряє на реєстрі `TEST_VARIANTS`).
2. Кожен тест має **критерій прийняття** (у `what`/`checkSteps` і в промті
   ревізії) — за яким числом/спостереженням обирається переможець.
3. Кожен запис має **правило прибирання** (`cleanupBy`) — умову, за якої його
   треба видалити.
4. Увесь код варіантів читає значення **лише через `getVariant(id)`**; ключ
   `localStorage` `budget_variants_v1` читається тільки в модулі реєстру
   (`<test-variants-module>` у `index.html`) і **не входить** у
   `BACKUP_LS_KEYS`.
5. Після рішення — **одна ревізія «finalize»**: видаляє програшні варіанти
   (код і гілки), запис реєстру, застарілі події/поля рекордера, що існували
   лише для порівняння; `pruneVariants()` при старті прибирає збережений вибір
   з `localStorage`. Поведінка для користувача після finalize — лише
   переможний варіант.
6. У `docs/ROADMAP.md` ведеться розділ **«Testing log»**: для кожного тесту —
   `id`, варіанти, рішення, дата (див. шаблон нижче).

## Як додати тест (запис реєстру `TEST_VARIANTS`)

```js
{
  id: 'kebab-case-id',              // унікальний, kebab-case
  title: 'Коротка назва',
  what: 'Одне речення: що саме перевіряємо.',
  variants: [                        // ≥2, ключі унікальні
    { key: 'a', label: 'Варіант A', hint: 'Що змінюється для користувача' },
    { key: 'b', label: 'Варіант B', hint: '…' },
  ],
  defaultVariant: 'a',               // серед variants
  addedIn: 'Rev X.Y.Z',              // ревізія, що додала тест
  cleanupBy: 'умова видалення',      // напр. «після рішення за логами X»
  checkSteps: ['Крок 1', 'Крок 2'],  // 2–3 кроки перевірки на пристрої
}
```

Код варіанта: `if(getVariant('kebab-case-id') === 'b'){ … } else { … }`.
Екран «Тестування» сам показує картку (назва, «Що перевіряємо», перемикач
варіантів із `hint`, позначка «типовий», `addedIn`/`cleanupBy`, «Як перевірити»,
«Записати лог із цим варіантом» — відкриває запис діагностики зі сценарієм
`<id>-<variant>`, «Скинути до типового»). Обраний варіант потрапляє в лог:
`device.variants` = `{ id: обраний_варіант }`.

## Шаблон запису «Testing log» (docs/ROADMAP.md)

| id | Варіанти | Рішення | Дата |
|---|---|---|---|
| `kebab-case-id` | `a` (типовий), `b` | обрано `b`: коротка причина з цифрами логів | YYYY-MM-DD |
