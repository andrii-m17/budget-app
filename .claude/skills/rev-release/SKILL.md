# Ревізія (Rev) від початку до push

Кожна зміна застосунку це окрема ревізія. Користувач відкриває PWA на iPhone, і Service Worker віддає кеш за `CACHE_NAME`, тому розбіжність версій означає, що зміни до телефона не дійдуть.

## Кроки
1. **Версія.** Збільш `APP_VERSION` в `index.html` і `CACHE_NAME` в `sw.js` однаково (`budget-app-v<версія>`). Одна задача = одна версія; кілька комітів = кілька версій.
2. **Коментарі.** Біля зміненого коду: `// Rev <версія>: <що й навіщо>`.
3. **Тести.** `node --test` має бути зеленим. Нові функції мають тести; змінена поведінка має оновлені тести.
4. **ROADMAP.** Запис у `docs/ROADMAP.md`:
   ```
   ### Rev <версія> <код задачі>: <назва>
   - Що: ... (1–3 пункти)
   - Чому: ...
   - Тести: +N, усього M
   - Перевірити на iPhone: ... (або «не потрібно»)
   ```
5. **STATUS.** Онови `docs/STATUS.md`: перенеси виконане, додай пункти «Чекає перевірки на iPhone», не чіпай розділ «Закрито».
6. **iPhone-чекліст.** Для класу ризику B з інтерфейсом і всього класу C у звіті напиши розділ «Для iPhone»; кроки в «Перевірки» (`CHECKS` в `index.html`) додає чат.
7. **Коміт.** Повідомлення: `Rev <версія> <код>: <коротко що>`.
8. **Тег і push.** `git tag -a rev-<версія> -m "Rev <версія>"`, потім `git push --follow-tags`. Гачок перед push сам перевірить тести, версії й ROADMAP; ручна перевірка: `node scripts/hooks/pre-push-guard.js --manual`.
9. **Звіт** за навичкою `task-report`.

## Відкат
`git revert <коміт>` → нова версія (крок 1) → запис у ROADMAP «відкат Rev X: причина» → push. Ніколи не `git push --force` у `main`.

## Типові помилки
- Змінив `APP_VERSION`, але не `CACHE_NAME` (або навпаки).
- Кілька змін в одній версії: потім неможливо відкотити одну.
- Скрипт масової заміни CSS або коду без перевірки на дублікати: після заміни шукай повтори блоків.
